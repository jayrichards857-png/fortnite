# SQLite → PostgreSQL migration — what was built, how it was verified, and the original design

**Status: IMPLEMENTED and tested on a local PostgreSQL 16.15; NOT deployed and NOT yet run against the real `data/pairplug.db`** (that file was never opened, copied, modified or migrated; all validation used disposable databases and databases produced by the application's own test flows). §A–§E are the results; §1 onward is the original plan, kept for the reasoning (a few details changed during the work; §A lists them).

## B. Transaction and concurrency decisions (the audit of every `tx` block)
SQLite's `BEGIN IMMEDIATE` serialised all writers, so many blocks were "read, decide, write" with no row protection. On PostgreSQL each one was classified and fixed:
* **Order state changes** all pass through `orderMachine.transition`, which now locks the order (`FOR UPDATE`) and keeps its conditional `UPDATE … WHERE status = <read>`. The order loaders used by buyer/seller/refund/review flows lock too, so a double-click or a retried request waits and then sees the committed result (idempotent "already confirmed" instead of a 409 or a double effect).
* **Inventory**: the unit hold is an atomic conditional `UPDATE … WHERE quantity > 0`; the purchase transaction locks the listing first, so "this buyer already holds a reservation", the hold and the order insert are one step (verified: 16 buyers racing for 4 units → exactly 4 orders; 8 parallel clicks by one buyer → exactly 1 order and 1 unit). `inventory.sync` locks the listing, and expiry uses `FOR UPDATE SKIP LOCKED` so overlapping job ticks release each stale reservation exactly once.
* **Label purchase** (money-adjacent): the claim of a stored quote now locks the quote **and checks the UPDATE's row count**. Before this change the row count was unchecked and a lost race could reach the carrier twice — a real hazard that SQLite's global lock had been hiding; it now has a deterministic regression test (and a mutation check that fails when the guard is removed).
* **Single-use links** (invitations, moderator setup links): the link row is locked inside the accepting transaction; the loser gets the same "invalid or already used" error as before.
* **Moderation actions**: the target account row is locked, so simultaneous bans/restrictions queue and the second sees the first ("already banned") — one ban, one log entry.
* **Rules without a single row to lock** (one open report per reporter+seller, one appeal at a time): transaction-scoped advisory locks (`lockKey`). **Caps** (sellers, moderators, moderator slots): the cap triggers take an advisory lock before counting.
* **Idempotent inserts** use `ON CONFLICT DO NOTHING` (webhook events, notifications, follows, favorites, cart, conversations); duplicate webhook events in parallel are processed once.
* Deadlocks (SQLSTATE 40P01) are retried automatically (bounded, 2 retries); transaction callbacks therefore contain only database work plus idempotent in-memory work.
* A failed SQL statement now aborts the whole PostgreSQL transaction (SQLite would continue); every `catch` around a statement inside a transaction either rethrows or sits outside it (verified by the full suite).

## C. Dialect differences that were fixed (and are easy to re-introduce)
`LIKE` is case-sensitive → `ILIKE`; scalar `MIN/MAX(a,b)` → `LEAST/GREATEST`; `strftime/date` → `to_char(to_timestamp(…))`; `group_concat` → `string_agg`; `json_extract` → `::jsonb ->>`; `GLOB` → regex check; `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`; `lastInsertRowid` → `RETURNING id`; SQLite lets a `WHERE`/`ORDER BY` expression use a select-list alias (PostgreSQL does not); NULL ordering (SQLite NULLs sort *first* ascending/*last* descending) → explicit `NULLS LAST` on `published_at`/`paid_at`/`latest` sorts; camelCase aliases need quotes; typed parameters in `COALESCE/CASE` need casts; a `CASE … THEN` inside a plpgsql `IF` must be parenthesised. A one-off static check prepared all 542 complete SQL string literals in `src/` against the migrated schema (541 OK; the 1 "failure" was a deliberately concatenated fragment); the 31 template-built queries were reviewed by hand and are exercised by the tests.

## D. Verification summary (all local, disposable data)
* `npm test`: **288/288** on PostgreSQL 16.15. `npm run check` clean. `npm audit`: 0 vulnerabilities (with `pg` 8.23.1). `npm run test:browser`: 6/6 journeys.
* Import: 28 SQLite v16 databases produced by the pre-migration application's test suite (real flows: escrow, ledger, disputes, shipments, reviews, moderation, chat…, 9,586 rows) imported with **all 145 checks each, 0 failures, source files untouched**; an independent second comparison (text serialization hashed separately) matched on users/listings/orders/events/messages/ledger/notifications/audit; the application booted on 14 of the imported databases and served 31–35 pages each (admin, moderation, orders, dashboards, storefronts) with no server errors.
* Mutation checks: removing the order lock, or the shipment-claim guard, makes the corresponding tests fail.

## E. Decisions D1–D5 as applied, and assumptions
* **D1** two stages (async on SQLite → PostgreSQL), SQLite dropped from the runtime (`node:sqlite` now appears only in `scripts/sqlite-to-pg.js`, `scripts/legacy/` and tests of the importer). **D2** `citext`. **D3** `pg` added; audit clean. **D4** epoch-second `BIGINT`, 0/1 `BIGINT` flags, cents unchanged (all `INTEGER` became `BIGINT`, so no 2038 limit; `pg` returns them as JS numbers — safe because every value is far below 2⁵³). **D5** tests run on PostgreSQL only, via `scripts/pg-test.sh` / `npm run test:pg:start`.
* Assumptions: PostgreSQL ≥ 13 (uses `DROP DATABASE … WITH (FORCE)` in tests; `citext` as a trusted extension); one app instance; default `READ COMMITTED` isolation (the locking above is designed for it); the database collation is not assumed (a `C`/`en_US` collation may order text differently from SQLite's binary order — only cosmetic ordering of equal-priority text); the owner role runs migrations and the importer.
* Pre-existing, unrelated: `scripts/seed-demo.js` already failed on the previous commit (it predates the Stripe-link/quantity rules); it was ported to a `pp_demo` PostgreSQL database but not repaired.

## F. Remaining risks / not done
* Not run on the real `data/pairplug.db`, a real VM, or a managed PostgreSQL (TLS, `citext` permission, pool limits, latency, failover are unverified there). Rehearse with `--dry-run` first (`docs/DEPLOYMENT.md` §8).
* No PostgreSQL → SQLite rollback tool: rolling back is lossless only until the new release accepts its first write.
* Photos remain on local disk (not backed up by `pg_dump`; `backup.js` copies new ones).
* The in-memory rate limiter / chat hub still require a single app instance.
* A static SQL check was a one-off (it needs a JS parser that is not a project dependency); regressions in untested dynamic queries are caught only by tests.

## 2. Proposed access layer and driver

* **Driver: [`pg`](https://node-postgres.com) (node-postgres) with `pg.Pool`.** Actively maintained, MIT, pure JS (no native build), no ORM — keeps the hand-written SQL that the 251 tests already exercise. Config: `DATABASE_URL` (+ `PGSSLMODE`/`DATABASE_SSL`), pool size small (default 10), statement timeout, `application_name=pairplug`.
* **Same surface, now async:** `await q.get(sql, …params)`, `await q.all(…)`, `await q.run(…)` (returns `{ changes, rows }`), `await q.insert(sql, …)` (returns the new id via `RETURNING id`), `await tx(async () => { … })`, `await getSettings()`, `await setSetting()`.
* **Transaction context via `AsyncLocalStorage`.** Inside `tx(async () => …)` every `q.*` call transparently uses the transaction's dedicated pooled client, so inner helper functions (`INV.holdUnit`, `notify`, …) need **no signature changes** — only `await`. Nested `tx()` joins the outer transaction (as SQLite's callers already assume). Serialization failures / deadlocks (`40001`, `40P01`) are retried a bounded number of times.
* **Startup is async:** `await db.ready()` (connect, run pending migrations under an advisory lock) replaces module-load migration. `createServer()` and `test/helpers.js` await it.
* **Safety net against a forgotten `await`:** in non-production, promises returned by `q.get` are wrapped so reading a property (e.g. `.id`) on an un-awaited result throws "missing await". Un-awaited `q.all` fails loudly on iteration/`.map`. Plus a script (`scripts/check.js` extension) that flags un-awaited calls to known-async functions.
* **Effect on call sites:** every function that touches the DB becomes `async` and every caller `await`s it — this cascades through routes, views that query, `chat/*`, jobs, and the WebSocket handlers (their `setInterval`/`message` callbacks need `.catch` handling). Express routes already use `wrap`. Pure functions (validation, formatting) stay sync.

## 3. Transaction guarantees (what replaces `BEGIN IMMEDIATE`)

SQLite serialised **all** writers, so many blocks do read-then-write safely. PostgreSQL does not, so each of the 82 `tx` blocks is audited and fixed to one of:

1. **Atomic conditional SQL** — e.g. inventory hold: `UPDATE listings SET quantity = quantity - 1 WHERE id=$1 AND status='active' AND quantity > 0` (rowCount must be 1). Under READ COMMITTED a concurrent updater re-evaluates the `WHERE` after the first commits, so exactly one buyer wins the last unit.
2. **State machine transitions** — `UPDATE orders SET status=$new … WHERE id=$1 AND status=$expected` (rowCount 0 ⇒ lost the race ⇒ 409), plus `SELECT … FOR UPDATE` when several rows must change together.
3. **Checkout expiry / auto-release jobs** — `SELECT … FOR UPDATE SKIP LOCKED` so concurrent job ticks (or instances) never process the same row twice.
4. **Consistent lock order** (listing → checkout → order → payment/ledger) to avoid deadlocks; retry on `40P01`.
5. **Append-only/immutable tables** (ledger, audit_log, case_events, order snapshot) keep their guarantees as `plpgsql` triggers.
6. Money stays **integer cents** (`BIGINT`); epoch-seconds timestamps stay `BIGINT`; 0/1 flags stay `INTEGER` — no behaviour change (decision D4).

## 5. Local test database
PostgreSQL 16 server binaries are installed in this environment (no cluster running). Tests will use a **disposable cluster initialised under the session scratchpad** (own port, trust auth on a unix socket, deleted afterwards), never a shared or hosted database. Hosted free PostgreSQL tiers are not assumed permanent (e.g. Render's free Postgres expires after 30 days and has no backups) and are not used.

## 6. Decisions requested before S1
* **D1** Approve the two-step approach (S1 async-on-SQLite, then S2 switch to PostgreSQL) and dropping the SQLite runtime after S2 (SQLite stays only as the *import source*).
* **D2** Case-insensitive columns via `citext` (needs `CREATE EXTENSION citext`; available on most managed PostgreSQL) rather than `lower()` indexes + query rewrites.
* **D3** Permission to add the `pg` dependency (`npm install pg`) and run `npm audit`.
* **D4** Keep epoch-second `BIGINT` timestamps, `INTEGER` 0/1 flags and cent integers (no `timestamptz`/`boolean` conversion in this phase).
* **D5** After S2 the test suite runs on PostgreSQL only (needs a local PG for `npm test`; documented helper script to start/stop the disposable cluster).

## 7. Known risks
* Large mechanical change; a missed `await` is the main bug class (mitigated by the guard + check script + full tests).
* Concurrency semantics change from "one global writer" to row-level; every `tx` block needs review (not just compilation).
* PG strictness (types, `GROUP BY`, NULL ordering, `ILIKE` semantics, collation of ordering) will surface latent bugs; fixing them is in scope, hiding them is not.
* Data migration correctness must be proven on real-shaped data before any cutover; cutover itself (not part of this phase) needs a maintenance window and the rollback plan in `docs/DEPLOYMENT.md`.
